### نموذج «لكل مشترك اعتماداته» (كما في الزكاة)
تكاملا شموس والسياحة **بمقابلٍ ماليّ**، وكل منشأةٍ مرخّصة تملك **وصولها
الحكومي الخاص** (بيانات اعتماد/توكن تصدرها لها الجهة). لذلك:
- **المشترك يرفع اعتماداته الخاصّة** (شموس · NTMP) في إعداداته.
- ضيوف يربط **نيابةً عنه** عبر محوّل محايد — فتنتقل **التكلفة والمسؤولية** للمشترك.
- ضيوف لا يحتفظ باعتمادٍ مركزيّ ولا يتحمّل الرسوم؛ عزلٌ تامّ لكل منشأة.
- منشأةٌ بلا اعتمادٍ مربوط: تُعرَض «غير مربوطة بشموس/السياحة» بلا ادّعاء امتثال.

## ١. WHAT / WHY

### المشكلة
تُلزم وزارة الداخلية (عبر شموس) كل مزوّد إقامة بتسجيل بيانات النزيل لحظياً
عند الدخول (وتحديثها عند المغادرة). شرطٌ قانونيّ للتشغيل — وسببٌ رئيسٌ
لتفوّق المنافسين المعتمَدين.

### النتيجة المطلوبة
عند إتمام تسجيل دخول نزيل في ضيوف:
1. تُجمَّع بيانات النزيل المطلوبة (هوية/إقامة/جواز · جنسية · وحدة · تواريخ).
2. تُرسَل إلى شموس عبر **محوّل معتمد** ضمن نافذةٍ زمنية.
3. تُخزَّن حالة التسجيل (مُسجَّل/فاشل/معلّق) ومرجع شموس.
4. عند المغادرة/الإلغاء يُحدَّث السجلّ وفق المتطلّب الرسمي.

## ٤. نموذج البيانات (مقترح)

```
gov_provider_config(client_id, service, credentials_enc, api_base,
                    enabled, env, created_at,
                    PRIMARY KEY(client_id, service))   -- service: shomoos | ntmp
                    -- اعتمادات كل مشترك، مشفّرة، لكل خدمة على حدة

gov_registrations(id, client_id, service, guest_id, booking_id,
                  dedup_key UNIQUE,          -- (service:guest_id:booking_id)
                  status,                    -- pending|registered|failed|rejected
                  gov_ref,                   -- مرجع الجهة (من الاستجابة)
                  request_raw, response_raw, -- تدقيق
                  attempts, created_at, updated_at)
```
- جدولٌ موحّد للخدمتين (شموس/NTMP) — نفس المنطق، محوّلٌ لكلٍّ.
- عزلٌ بـ`client_id`؛ `dedup_key` فريد يمنع التسجيل/الإبلاغ المزدوج.
- اعتمادات كل مشترك مشفّرة (نمط `guest_encryption`، مفتاح منفصل).

## ٥. حدود الأخطاء

| الحالة | التصرّف |
|---|---|
| بيانات نزيل ناقصة | يُمنع إتمام الدخول أو يُعلَّم «تسجيل شموس معلّق» بوضوح — لا تسجيلٌ صامتٌ ناقص |
| فشل شبكة | طابور + إعادة محاولة + تنبيه؛ لا يُبتلع |
| تكرار | يُكشف بـ`dedup_key` |
| رفض من شموس | يُخزَّن السبب ويُعرَض للمنشأة للتصحيح |
| غياب المواصفة الرسمية | **لا كود سلك افتراضي** — المحوّل يبقى واجهةً معلَّمة `NotImplemented` حتى الاعتماد |

## ٦. خطة الاختبار

1. **وحدة:** بناء حزمة النزيل الداخلية + `dedup_key` + منطق إعادة المحاولة (كلّها بلا شبكة).
2. **عقد المحوّل (Contract):** اختبار حدود المحوّل بـ**Fake Shomoos** يطابق العقد المتوقّع — يُستبدَل بالحقيقي عند توفّر المواصفة.
3. **كسر:** نزيل بلا هوية → يُمنع/يُعلَّم؛ إرسال مكرّر → صفٌّ واحد.
4. **Reconciliation:** حجز check-in بلا تسجيل → تُبرزه المهمة.

**معيار القبول (المرحلة الأولى):** كل المنطق الداخلي مبنيّ ومختبَر خلف واجهة المحوّل؛ المحوّل الحقيقي يُفعَّل فقط بعد الحصول على **المواصفة/الاتفاقية الرسمية** واعتماد ضيوف كمزوّد.
