# مواصفة: تكامل ZATCA المرحلة ٢ (الفوترة الإلكترونية — فاتورة)

**الحالة:** Draft · **الأولوية:** P0 (إلزامي — موجة ٢٤ تشمل كل فندق، أبريل–يونيو ٢٠٢٦)
**المصدر:** توثيق ZATCA/Fatoora الرسمي فقط. لا يُبنى شيءٌ على افتراض.

---

## ١. WHAT / WHY (المواصفة)

### المشكلة
كل منشأةٍ عاملة ملزمةٌ بإصدار فواتير إلكترونية موقَّعة تشفيرياً ومربوطة بمنصّة
«فاتورة» التابعة لهيئة الزكاة والضريبة والجمارك. بدون هذا، لا يمكن للمنشأة
التشغيل قانونياً — وهو شرط أهلية لعملاء ضيوف.

### النتيجة المطلوبة
عند إصدار فاتورة في ضيوف (نقدية/بطاقة/تحويل، عند الدخول أو المغادرة):
1. تُبنى فاتورة **UBL 2.1 XML** صحيحة.
2. تُختَم تشفيرياً (Cryptographic Stamp) بمفتاح المنشأة.
3. **فاتورة مبسّطة (B2C — النزلاء الأفراد):** تُبلَّغ (Reporting) خلال ٢٤ ساعة، ويُطبع QR فوراً.
4. **فاتورة قياسية (B2B — عملاء الشركات):** تُخلَّص (Clearance) لحظياً قبل تسليمها للعميل.
5. يُحفظ كل شيء في سجلّ تدقيق، ويُعاد الإرسال عند الفشل بلا تكرار.

### خارج النطاق
- محرّك المحاسبة نفسه (موجود) — هذا تكامل الفوترة فقط.
- التقارير الضريبية الدورية (منفصلة).

## ٢. المتطلّبات الوظيفية (موثّقة رسمياً)

| # | المتطلّب | ملاحظة |
|---|---|---|
| F1 | توليد فاتورة UBL 2.1 (Standard/Simplified) | حسب مخطّط ZATCA |
| F2 | حقول إلزامية: UUID · ICV (عدّاد تصاعدي لكل منشأة) · PIH (تجزئة الفاتورة السابقة) · وقت الإصدار | ICV وPIH يربطان السلسلة |
| F3 | الختم التشفيري: توقيع ECDSA على منحنى secp256k1، تجزئة SHA-256 | من مفتاح المنشأة |
| F4 | رمز QR بصيغة **TLV** مُرمَّز Base64 (البائع · الرقم الضريبي · الوقت · الإجمالي · الضريبة · تجزئة · توقيع · مفتاح عام) | يُطبع على الفاتورة |
| F5 | **Simplified**: استدعاء Reporting API خلال ٢٤ ساعة | B2C |
| F6 | **Standard**: استدعاء Clearance API لحظياً | B2B — الفاتورة غير صالحة قبل التخليص |
| F7 | إشعارات دائنة/مدينة (Credit/Debit Notes) بنفس المسار | مع سبب الإشعار |
| F8 | معالجة الاستجابة: `CLEARED` / `REPORTED` / `WARNING` (مقبول مع ملاحظات) / `ERROR` (مرفوض) | تُخزَّن كلها |

### التأهيل (Onboarding) — مرّة لكل منشأة
| # | الخطوة | API |
|---|---|---|
| O1 | توليد زوج مفاتيح + CSR بحقول المنشأة | محلي |
| O2 | الحصول على **Compliance CSID** | Compliance CSID API |
| O3 | اجتياز فحوص الامتثال (٦ عيّنات فواتير: قياسية/مبسّطة + إشعاراتها) | Compliance Invoice API |
| O4 | الحصول على **Production CSID** | Production CSID API |
| O5 | تخزين CSID والمفتاح الخاص مشفّرَين (كتشفير النزلاء) | — |

## ٣. المتطلّبات غير الوظيفية

- **Idempotency:** مفتاح فريد لكل فاتورة (UUID) — إعادة الإرسال لا تُنشئ فاتورةً ثانية.
- **Retry + Backoff:** فشل الشبكة → إعادة أسّية (كما في `services/dunning.py`).
- **Audit:** جدول `zatca_invoices` يحفظ الطلب والاستجابة الخام + الحالة + التوقيت.
- **Reconciliation:** مهمة دورية تُطابق فواتير ضيوف بحالتها لدى ZATCA وتُبرز المتخلّفة.
- **العزل:** كل صفٍّ بـ`client_id`؛ CSID ومفتاح كل منشأة منفصلان تماماً.
- **الأمان:** المفتاح الخاص لا يخرج عبر HTTP أبداً؛ يُخزَّن مشفّراً (`GUEST_ENCRYPTION_KEY` نمطاً مماثلاً بمفتاح منفصل `ZATCA_KEY_ENCRYPTION`).
- **Sandbox أولاً:** كل مسارٍ يُختبَر في بيئة ZATCA التجريبية قبل الإنتاج، بعلَمٍ `ZATCA_ENV=sandbox|production`.

## ٤. نموذج البيانات (مقترح)

```
zatca_credentials(client_id PK, csid_compliance, csid_production,
                  private_key_enc, onboarding_status, env, created_at)
zatca_invoices(id, client_id, invoice_uuid UNIQUE, icv, pih, invoice_type,
               invoice_hash, xml_signed, qr_tlv, status, zatca_response,
               submitted_at, created_at)
```
- `invoice_uuid` فريد → Idempotency على مستوى القاعدة.
- `icv` تصاعديّ لكل `client_id`؛ `pih` = تجزئة فاتورة `icv-1`.

## ٥. حدود الأخطاء (لا يُتساهل فيها)

| الحالة | التصرّف |
|---|---|
| توقيع/تجزئة خاطئة | إيقاف قبل الإرسال — لا تُرسَل فاتورة معطوبة |
| استجابة `ERROR` (رفض) | تُخزَّن، تُعرَض للمنشأة، تُمنع طباعة فاتورة «صالحة» |
| استجابة `WARNING` | مقبولة، لكن تُسجَّل الملاحظات وتُعرَض |
| انقطاع شبكة (Simplified) | تُوضَع في طابور وتُعاد ضمن نافذة الـ٢٤ ساعة |
| انقطاع شبكة (Standard) | الفاتورة **معلّقة** — لا تُسلَّم للعميل حتى التخليص |
| تكرار إرسال | يُكشف بـ`invoice_uuid` — يُعاد نفس النتيجة لا فاتورة جديدة |

## ٦. خطة الاختبار (Break-before-trust)

1. **وحدة:** بناء UBL · حساب PIH/ICV · TLV QR · التوقيع — بمتّجهات اختبار ZATCA الرسمية المعروفة النتيجة.
2. **كسر:** فاتورة بتوقيعٍ خاطئ → تُرفض قبل الإرسال (تأكيد الحارس يعمل).
3. **تكامل Sandbox:** المرور بكل O1–O5 ثم Reporting/Clearance لعيّناتٍ حقيقية.
4. **إيديمبوتنسي:** إرسال نفس الـUUID مرّتين → نتيجة واحدة، صفٌّ واحد.
5. **Reconciliation:** حقن فاتورة «مُرسَلة بلا تأكيد» → تُبرزها المهمة الدورية.

**معيار القبول:** كل عيّنات فحص الامتثال الستّ تنجح في Sandbox، ولا تُطبع فاتورةٌ «صالحة» إلا بحالة `CLEARED`/`REPORTED`.
