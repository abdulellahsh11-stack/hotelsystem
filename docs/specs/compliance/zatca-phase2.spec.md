# مواصفة: ZATCA المرحلة ٢ — **تكامل خارجيّ مع مزوّد معتمَد (عند الطلب)**

**الحالة:** Draft · **الأولوية:** P0 · **النموذج:** Provider-Delegated (ترحيل المسؤولية)

---

## قرار النطاق (حاسم)

**ضيوف يقدّم «المحاسبة العامة» فقط** — القيود والفواتير ودفتر الأستاذ هي
مصدر الحقيقة المالي. أمّا التوقيع التشفيري والتخليص/الإبلاغ لدى «فاتورة»
(ZATCA) **فيُرحَّل بالكامل إلى مزوّد حلٍّ معتمَد من ZATCA** عبر API عند الطلب.

**لماذا:**
- **ترحيل المسؤولية القانونية**: المزوّد المعتمَد هو «Solution Provider» المسؤول أمام ZATCA؛ ضيوف نظام محاسبة عام يتّصل عند الحاجة.
- **تقليل المخاطر والبناء**: لا onboarding CSID ولا ECDSA ولا UBL/TLV داخل ضيوف — كلّها عند المزوّد.
- **مرونة**: أي منشأةٍ تربط مزوّدها المعتمَد؛ ضيوف محايدٌ تجاه المزوّد (Provider-agnostic).

**خارج نطاق ضيوف (مسؤولية المزوّد):** توليد المفاتيح · CSID · UBL 2.1 ·
الختم ECDSA · PIH/ICV · TLV QR · نداءات Clearance/Reporting لـ«فاتورة».

**داخل نطاق ضيوف:** نموذج فاتورة/قيد محاسبي عام · محوّل مزوّد (Adapter) ·
إرسال البيانات عند الطلب · تخزين المرجع والحالة وQR الراجع · عرضها للمنشأة.

### كل مشترك ومزوّده (Per-Tenant Provider)
**كل منشأةٍ تختار مزوّدها المعتمَد وتُدخل مفاتيح API الخاصّة بها.** ضيوف لا
يفرض مزوّداً واحداً: `zatca_provider_config` صفٌّ لكل `client_id` يحمل
`provider` و`api_base` واعتماداته المشفّرة. فمنشأةٌ تستخدم ClearTax وأخرى
InvoiceQ وثالثةٌ Wafeq — كلٌّ عبر نفس المحوّل المحايد، وبعزلٍ تامّ. تبديل
المشترك لمزوّده = تحديث صفّه فقط، بلا مساسٍ بالبقيّة.

---

## ١. WHAT / WHY

عند إصدار فاتورة في ضيوف، وإن كانت المنشأة قد ربطت مزوّداً معتمَداً:
1. تُبنى **حمولة فاتورة عامّة** (بنود · ضريبة · عميل · إجمالي) من المحاسبة.
2. تُرسَل إلى **المزوّد المعتمَد** عبر محوّله عند الطلب.
3. يعيد المزوّد: حالة (`cleared`/`reported`/`rejected`) · معرّف ZATCA · QR · XML مُخلّص.
4. يخزّن ضيوف المرجع والحالة وQR للعرض والتدقيق — **لا يحتفظ بمسؤولية التوقيع**.
5. إن لم تُربط منشأةٌ أيّ مزوّد: الفاتورة تبقى «محاسبة عامّة» فقط، مع تنبيهٍ أن الامتثال يتطلّب ربط مزوّد.

---

## ٢. المزوّدون المرشّحون (يتطلّب تأكيد الاعتماد الحالي لدى ZATCA)

مزوّدون يقدّمون API للتكامل (من بحثٍ عام — **يجب تأكيد اعتمادهم الجاري في القائمة الرسمية لـZATCA قبل الاختيار**):

| المزوّد | ملاحظة |
|---|---|
| InvoiceQ | نظام فوترة موصوفٌ كمؤهَّل لمرحلة ٢ |
| ClearTax (Clear) | مزوّد امتثال إقليمي بواجهات API |
| SowaanERP · Trax Group | حلول ERP متوافقة |
| Wafeq · Qoyod · Mekyal · Complyance | مرشّحون إضافيون (تأكيد الاعتماد مطلوب) |

> **قاعدة `TODO`:** تُثبَّت القائمة من **القائمة الرسمية لمزوّدي الحلول المعتمَدين لدى ZATCA**، ولا يُعتمَد مزوّدٌ إلا بعد التحقق من اعتماده الجاري وتوقيع اتفاقية معالجة بيانات (DPA).

**معايير الاختيار:** اعتماد ZATCA جارٍ · API موثّق (Clearance+Reporting) · SLA وزمن استجابة · اتفاقية معالجة بيانات (PDPL) · تسعير لكل فاتورة/اشتراك · دعم عربي · Sandbox.

## ٣. التصميم (محوّل مزوّد محايد)

```
ضيوف — المحاسبة العامة (مصدر الحقيقة)
        │  حمولة فاتورة عامّة (عند الطلب)
        ▼
ZATCA Provider Adapter (واجهة موحّدة)   ← محوّل لكل مزوّد
        │
        ▼
المزوّد المعتمَد  →  «فاتورة» / ZATCA   (المسؤول عن التوقيع والتخليص)
        │
        ▼
حالة + معرّف + QR + XML مُخلّص  →  يُخزَّن في ضيوف للعرض والتدقيق
```

واجهة موحّدة (Provider-agnostic):
```
class ZatcaProvider(Protocol):
    def submit_invoice(payload) -> {status, zatca_id, qr, xml, raw}
    def submit_credit_note(payload) -> {...}
    def status(zatca_id) -> {...}
```

## ٤. نموذج البيانات

```
zatca_provider_config(client_id PK, provider, api_base, credentials_enc,
                      env, enabled, created_at)          -- ربط المنشأة بمزوّدها
zatca_submissions(id, client_id, invoice_id, dedup_key UNIQUE,
                  provider, status, zatca_id, qr, xml_ref,
                  request_raw, response_raw, attempts, created_at)
```
- عزلٌ بـ`client_id`؛ `dedup_key` (invoice_id) يمنع الإرسال المزدوج.
- بيانات اعتماد المزوّد مشفّرة (نمط `guest_encryption`، مفتاح منفصل).

---

## ٥. المتطلّبات غير الوظيفية
- **Idempotency**: إرسالٌ واحد لكل فاتورة (`dedup_key`) — إعادة المحاولة لا تُنشئ إرسالاً ثانياً.
- **Retry/Backoff**: فشل شبكة المزوّد → إعادة أسّية + طابور (نمط `dunning`).
- **Audit**: طلب/استجابة المزوّد خامّان في `zatca_submissions`.
- **Reconciliation**: مهمة دورية تُبرز الفواتير غير المُخلّصة/المرفوضة.
- **عدم الادّعاء**: فاتورةٌ بلا مزوّدٍ مربوط تُعرَض «محاسبة عامّة — غير مُقدَّمة لـZATCA»، لا «متوافقة».
- **العزل**: كل منشأة ومزوّدها واعتماداتها منفصلة.

## ٦. حدود الأخطاء
| الحالة | التصرّف |
|---|---|
| لا مزوّد مربوط | فاتورة محاسبة عامّة + تنبيه صريح (لا ادّعاء امتثال) |
| رفض المزوّد (`rejected`) | يُخزَّن السبب ويُعرَض؛ لا تُعامَل كمُخلّصة |
| انقطاع شبكة المزوّد | طابور + إعادة؛ لا يُبتلع |
| تكرار | يُكشف بـ`dedup_key` — نفس النتيجة |
| مزوّد غير معتمَد | يُمنع ربطه (تحقّق من قائمة ZATCA) |

## ٧. خطة الاختبار
1. **وحدة**: بناء حمولة الفاتورة العامّة + `dedup_key` + إعادة المحاولة (بلا شبكة).
2. **عقد المحوّل**: Fake Provider يطابق الواجهة الموحّدة — يُستبدَل بالمزوّد الحقيقي في Sandbox.
3. **كسر**: إرسال بلا مزوّد → لا ادّعاء امتثال؛ إرسال مكرّر → صفٌّ واحد؛ رفض المزوّد → لا يُعرض «مُخلّص».
4. **Sandbox المزوّد**: دورة كاملة لفاتورة قياسية ومبسّطة وإشعار دائن.
5. **Reconciliation**: فاتورة «مُرسَلة بلا تأكيد» → تُبرزها المهمة.

**معيار القبول:** ضيوف يبني الحمولة ويُرسل عند الطلب ويخزّن ويعرض النتيجة عبر محوّلٍ محايد؛ لا توقيعٌ ولا تخليصٌ داخل ضيوف؛ ولا فاتورةٌ تُعرَض «متوافقة» إلا بحالة `cleared`/`reported` من مزوّدٍ معتمَد.
